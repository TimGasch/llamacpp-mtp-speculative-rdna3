**What v3 changed, and its cost:** v3 adds two patches (0006, 0007; §5) that remove the TTFT
regression. The protocol's ≤ 5 % TTFT/pp side condition is now met on the median of every
workload class (short prompts, and each long document), for both models.
- **The cost is long-context Qwen speed:** 1.682× in #3 against 1.766× in #2 (different
  sessions; on dev, within one session, −3.5 %, not significant). The windowed drafter sees
  only the last 2,048 prompt tokens.
- **Individual short prompts still exceed 5 %:**
  - Qwen: up to +7.4 % TTFT and −10.5 % engine-reported pp.
  - Gemma: up to +13.2 % TTFT and −6.2 % pp.
- **How much of that is noise:** for TTFT, the same build in two blocks of one session differs
  by up to 34 % on single short prompts. Engine-reported pp is much steadier (≤ 3.7 %), so the
  Qwen pp extremes are real (`results/raw/phase3/ttft_noise_eval3.json`).

**Quality:**
- **Q2 passes everywhere:** **zero hard divergences** in free-running greedy generation, for
  both models and in all three evaluations.
- **Bit-identical to stock:** every target-model execution path of every build I measured gives
  logits **bit-identical** to a stock llama.cpp b11284 path (equal dump hashes). This covers
  decode (ub=1), verify (ub=4), prompt (ub=512) and, new in evaluation #3, the 16-token-batch
  path (ub=16) used for short prompts.
- **New finding: Q1 fails for stock's own 16-token path.** On the holdout set, stock llama.cpp's
  ub=16 path lies **outside** the Q1 noise envelope that Amendment 1 defines from three other
  stock variants:
  - Qwen: mean KLD 5.21e-4 vs 5.14e-4, p99 4.27e-3 vs 4.04e-3.
  - Gemma: mean KLD 2.33e-3 vs 1.75e-3, p99 3.13e-2 vs 2.11e-2.

  Sources: `results/raw/q1/gate_holdout_*_stock-ub16.gate.json`.
- **What that means for the gate:**
  - R itself uses this path for every short prompt.
  - The evaluation #1 build has the same ub=16 logits (hashes `050cfb3b`, `e3f93566`), so its
    earlier "Q1 PASS" covered only ub=1/4/512.
  - Read literally (A1.1: "every path … plus its prompt path"), **Q1 fails for v3, for every
    earlier build, and for stock llama.cpp itself.** `gate_holdout_*_final-v3.gate.json`
    records `PASS=False` for this reason.
- **Two consistent readings, and your call:**
  - **(a) Strict letter:** no build, including unmodified llama.cpp, can pass Q1, and no
    success level can be claimed.
  - **(b) Intent of the amendment** ("stay within stock llama.cpp's own numerical variation"):
    all v3 paths are bit-identical to stock, which is the strongest possible form of that, and
    the result is "partial success".
  - Choosing (b) formally would need a second, post-hoc amendment that adds R(ub=16) to the
    envelope. That is why I am not making it myself.
- **Plain decoding unchanged:** plain non-speculative decoding is unchanged (0.992–1.003× in
  llama-bench).

**Where the speed comes from.** Almost all of it is **speculative decoding with multi-token-
prediction (MTP) drafters, a stock llama.cpp feature**. Configured well, stock alone reaches
1.635× (Qwen) and 2.072× (Gemma) in evaluation #3.
- **Qwen:** my additions (patches 0001–0003, 0006, 0007 plus local MTP sidecar files) add
  **+15.9 %** on S-greedy (1.159× [1.136, 1.185] vs stock speculation in the same session).
- **Gemma:** they add nothing. C vs S is 0.994× [0.992, 0.996] on S-greedy (the same in
  evaluation #1) and 1.000× on S-sampled.
  - The kernel fixes don't touch Gemma's admissible execution path.
  - Gemma's faster draft-length-4 setting was **excluded by the quality gate**, because stock's
    own 5-token verify numerics fall outside the envelope.

**Why not 2–3× across the board:**
- **Roofline:** batch-1 decoding already runs at about 70 % of the card's memory bandwidth, so
  kernel work alone is capped at about 1.4× (§7).
- **Speculation:** its gain is limited by three things:
  - draft acceptance, about 72 % per drafted token for Qwen and 57 % for Gemma at n=3 on the
    dev set (`results/raw/20261001-001024_p2b-screen`)
  - the cost of verifying several tokens at once
  - drafting and host-side work. In a Qwen v3 speculative step of 17.8 ms (dev, diagnostic
    build with wall-clock timers):
    - 12.8 ms is the GPU wait for the 4-token verify
    - 2.45 ms is drafting
    - about 2.6 ms is submission, sampling and bookkeeping

    The verify mat-vecs already run at 416–504 GB/s, and only about 2 % is safely removable
    (§6, last rows).
- **Sampling and long contexts:** gains are smaller with sampled generation and long contexts.

**Answer to "is 2–3× realistic on this machine?"**
- **About 2× for greedy chat/code workloads is realistic today**, mostly by using llama.cpp's own
  MTP speculation correctly, plus targeted fixes.
- **A robust 3× with unchanged quality is not realistic** with these models on this GPU. The
  evidence:
  - Longer drafts do not pay. Stock Qwen collapses beyond 3 draft tokens. After my kernel fix,
    and even with confidence-gated drafting, n=4–8 is not faster than n=3 (§6, JOURNAL
    Phase 2b; n=4 re-tested in Phase 2c).
  - Gemma's longer drafts are not admissible under the quality gate.
  - Everything else (kernels, host overhead) is bounded well below the missing factor.

## 3. Method

- **Protocol:** `PROTOCOL.md` v1.0 was approved before any measurement. **Amendment 1** was
  approved after Phase 1 and before any optimization result existed; it is in §12 of the
  protocol.
- **Measurement tooling** (`bench/`): frozen and checksummed (tags `bench-frozen` and
  `bench-frozen-a1`, manifest sha256 `65baadf4…`), and verified before every run.
- **Speed:** measured client-side on real prompts through llama-server's streaming API, one
  timestamp per token. Reported: median, IQR, CV and a 95 % bootstrap CI over prompts. Engines
  are interleaved (R C S S C R), and a llama-bench canary runs at the start and end of every
  session. Session validity requires canary drift ≤ 3 %.
- **Quality gates:**
  - **Q1:** teacher-forced full-vocabulary KL divergence, top-1 agreement and perplexity
    against R's single-token decode path. Each execution path must lie inside the **noise
    envelope** of llama.cpp's own stock variants: prompt path ub=512, verify path ub=4, and
    flash attention off. See §3.1 for why.
  - **A1.2 design rule:** no lossy technique that stock llama.cpp does not already use.
  - **Q2:** free-running greedy generation with **zero hard divergences**. A divergence is hard
    if C picks a token that R rates more than 0.25 nats below its top token.
- **Holdout:** 15 prompts, 9 Q1 segments (5,120 scored positions) and 3 long documents per model.
  These were sealed until Phase 3. The access log `results/holdout_access.log` shows its first
  entry at 22:22:56, in Phase 3.

### 3.1 Why the quality thresholds had to be amended (an important finding in itself)

My Phase 0 thresholds assumed that kernel-level numerical noise would be one to two orders of
magnitude below 1e-3 mean KLD. The Phase 1 noise-floor measurement disproved that. llama.cpp's
own stock variants differ from its single-token decode path by a mean KLD of 1.6–2.2e-3 and a
top-1 agreement of 98.1–98.6 % (`results/raw/q1/noisefloor_*`, JOURNAL entry 004).

The main cause is visible in the source. On AMD, the Vulkan backend quantizes activations to int8
(q8_1) for every batched matmul (`ggml_vk_should_use_mmvq`), but not always for single tokens.
With the original thresholds, stock llama.cpp's own speculative verification and even its prompt
path would have "failed" its own quality gate.

The user chose option A: the envelope gate plus the design rule. The calibrators show that the
envelope still rejects real quality loss:
- KV-cache q4_0 is 5–25× outside the envelope.
- A different Q4_K_M quantization of Qwen is 8× outside.

8-bit KV lands *inside* the envelope, which is why the design rule A1.2 exists
(`results/raw/q1/envelope-check_*_dev.gate.json`).

## 5. Where the speed comes from (attribution)

Speculative decoding is the only lever large enough for ≥ 2×; see §7.

**Stock llama.cpp b11284 already contains** speculative decoding:
- multi-token prediction (MTP) heads
- EAGLE3
- DFlash/DSpark
- n-gram drafting
- Google's official Gemma 4 "assistant" MTP drafter

It also contains recurrent-state rollback for hybrid models. The honest split is therefore:

1. **Stock features, correctly configured.** This is the secondary reference S: MTP drafting,
   with a draft length tuned on dev.
   - For Qwen3.5 this needed an MTP-only "sidecar" file. The unsloth MTP GGUF's main weights
     differ from the target file in 248 of 427 tensors, so it could not be used directly.
   - The sidecar (`scripts/make_mtp_sidecar.py`) copies the target's embedding and head
     byte-identically and adds only the 15 MTP-block tensors. The target file used with `-m`
     is never changed.
2. **My changes on top of stock**, in `patches/llama.cpp/0001–0003` against b11284:
   - **0001 — Vulkan MMVQ decode-once (Q4_K/Q5_K/Q6_K).** The batched mat-vec kernel re-unpacked
     each weight block for every column. That made speculative verification ALU-bound and
     pathological at 5–7 columns: the stock Qwen `MUL_MAT_VEC q4_K` at n=6 took 622 µs vs.
     120 µs at n=8 (`results/raw/phase1/explore/perflog_qwen_k*.txt`). The fix decodes once per
     row. Output is **bit-identical** to stock (qdump hashes equal, `results/raw/q1/it01_bitcheck_*`).
   - **0002 — RDNA3 rows-per-workgroup** for more than 4 columns. Also bit-identical
     (`results/raw/q1/it02_bitcheck_*`).
   - **0003 — reduced-vocabulary MTP draft head for Qwen3.5** (FR-Spec style; `d2t` mapping as in
     stock EAGLE3). Each draft step multiplies with 65,536 instead of 248,320 head rows, i.e.
     220 MB instead of 834 MB. Draft tokens can only come from that set; the unchanged target
     verifies every token, so emitted outputs cannot change. The vocabulary was ranked on
     WikiText-2 *train* plus Python library code plus dev-split generations. Cross-validated
     coverage is 98.45 % of generated tokens (JOURNAL, iteration 3).
   - **v2 draft sidecar (Phase 2b, dev-only decision, evaluation #2):** a 32k-token head, with
     the whole draft sidecar requantized to Q4_K via `llama-quantize --pure`. On dev this gave
     +6.2 % over the rv64k Q6_K sidecar with unchanged acceptance. The draft is exempt from
     design rule A1.2, because the target verifies every token.
   - **0006 — medium MMQ tile for small batches (Phase 2c, v3).** Without coopmat2, stock
     selects the small 32×32 MMQ tile for batches of n ≤ 32 tokens, and that tile is very slow
     on this RDNA3 GPU. Short prompts and llama-server's checkpoint-split prompt chunks hit it.
     The patch uses the medium tile there.
     - Bit-identical to stock (ub=16 dump hashes equal).
     - Qwen 9–32-token prefill drops from 89.2 to 57.0 ms in llama-bench
       (`results/raw/phase2c/ppsweep_*`).
     - It helps R-style plain use as much as speculation.
   - **0007 — MTP prompt window (Phase 2c, v3, draft-only).** During prefill, the stock MTP
     drafter runs its layer over every prompt token, which made Qwen's long-prompt TTFT
     6.4–7.3 % worse. With the patch, the drafter only buffers the last W = 2,048 prompt
     positions and decodes them once when the prompt is complete.
     - The environment variable `FASTLLAMA_MTP_PROMPT_WINDOW` sets W; 0 restores stock behaviour.
     - The target computation is untouched.
     - The cost: on long documents, the drafter sees less context.

## 7. Why kernel work alone cannot reach 2× (roofline)

Batch-1 generation must read every weight once per token:
- 5.10 GB per token for Qwen3.5-9B Q4_K_M
- 5.18 GB per token for Gemma 4 E4B Q8_0 (including the tied 0.71 GB output head)

Source: `results/raw/phase1/gguf_inventory_*.json`. Stock llama.cpp generates at 89.55 t/s
(Qwen) and 83.25 t/s (Gemma) (`results/raw/phase1/explore/llama-bench_ref_*.jsonl`). That is
already about 456 and 431 GB/s, 73 % and 69 % of the card's 624 GB/s spec bandwidth. Even a
perfect kernel running at the full spec bandwidth could therefore only reach **1.37× (Qwen) and
1.45× (Gemma)**.

My decode-path changes are bit-identical, and the single-token decode kernels are unchanged, so
plain (non-speculative) generation speed is unchanged, as expected.

Every factor beyond about 1.4× has to come from producing several tokens per pass over the
weights. That means speculative decoding, whose gain depends on the content.

## 8. Known limitations

- **Most of the speedup is a stock llama.cpp feature.**
  - For **Gemma 4 E4B**, the final configuration is functionally identical to stock llama.cpp
    with Google's MTP drafter at n=3. My kernel changes do not touch its admissible execution
    path.
  - Gemma n=4 was faster on dev, but stock's own ub=5 verify numerics fall outside the Q1
    envelope. My fix for that (float activations in verification, iteration 4) was
    numerically excellent but 14–25 % slower.
  - My own contribution is Qwen-specific. Over stock speculation in the same session it is:
    - +14.0 % in holdout evaluation #1
    - +16.5 % in #2
    - +15.9 % in #3

    It comes from the MMVQ fixes, the reduced-vocabulary draft head and, in v3, the TTFT
    patches. For Gemma, C vs S on S-greedy is 0.994× [0.992, 0.996] in both evaluation #1 and
    #3: a small, reproducible slowdown whose cause I did not investigate.
- **TTFT with MTP (fixed on medians in v3, not for every prompt).**
  - **Stock behaviour:** the stock MTP drafter processes the whole prompt as well. Final and
    v2 were therefore up to 6.6 % (Qwen, long prompts) and 8.9 % (Gemma, short-prompt median)
    slower to the first token.
  - **What v3 fixes:** patches 0006 and 0007 bring every workload median within 5 %.
  - **What remains:** individual short Qwen prompts are still up to 10.5 % slower in
    engine-reported prompt throughput. This exceeds same-engine noise (≤ 3.7 %), so the
    drafter's own prompt pass still costs something on short prompts.
  - **Cost of the window:** long-context Qwen tg falls (1.682× in #3 vs 1.766× in #2). The
    windowed drafter sees only the last 2,048 prompt tokens. W is a trade-off and was not
    tuned.
- **Stock inefficiencies that I found but did not fix:**
  - Gemma's flash-attention prefill with head size 512 on a 32 KB-shared-memory GPU: at 16k
    depth it is 4.65× slower than flash attention off (`results/raw/phase1/explore/gemma_fa_depth16k.jsonl`).
    This makes Gemma's 32k TTFT about 71 s.
  - The MMQ path for 33–64-token batches; patch 0006 fixes only n ≤ 32. Verify batches above
    8 tokens are about 7× the single-token cost.
  - llama-server's checkpoint-driven prompt splitting for hybrid/SWA models (§6). It costs up
    to two extra weight passes per prompt and was deliberately left unchanged.
  - These affect R and C alike, so fixing them would improve absolute TTFT.
- **Q1 gate and stock's own 16-token path (open, the user's decision).** On the holdout set,
  stock llama.cpp's ub=16 prompt path lies outside the Amendment 1 envelope for both models
  (§1, §4). Every build, including R, executes that path for short prompts with bit-identical
  logits. A1.1 read literally therefore fails every engine. Evaluations #1/#2 had not tested
  this path. I did not amend the envelope: adding R(ub=16) now would be a post-hoc change after
  the results are known, and the protocol leaves that to the user.
- **The holdout set was used three times** (evaluations #1–#3). Every decision between them was
  made on dev data only, and the access log shows only Phase 3 accesses. Still, #2 and #3 are
  weaker evidence than #1.
- **The plain-decoding llama-bench check (§4) was measured for the evaluation #1 build only.**
  v3 differs from it only in the MMQ tile for 9–32-token batches and in the drafter. Neither is
  used in single-token decoding or in the pp512 test, but this was not re-measured.
- **The quality gate was amended once.** This happened after the Phase 1 noise-floor
  measurement, before any optimization result, with the user's approval (§3.1). Under the
  original absolute thresholds, stock llama.cpp's own batched paths fail, and **every**
  speculative method (stock or mine) would be inadmissible. The target computation of every
  final build is bit-identical to stock on every path measured (ub=1/4/16/512). Whether a gate
  passes therefore depends only on how the envelope treats stock's own paths (see the ub=16
  item above). The only change to emitted-token numerics versus plain decoding is the one stock
  speculation already makes.
- **Speedups depend on content.** They were measured on 15 holdout prompts (5 categories × 3)
  plus 3 long documents. The bootstrap CIs reflect the variation between prompts. Qwen ran in
  its default thinking mode; the verbose reasoning style is fairly predictable, which favors
  drafting. Sampled generation (S-sampled) gains less than greedy generation.
- **The draft vocabulary was chosen with dev-split generations** (weighted 5×). The rv32k head
  of evaluation #2 relies more on that than rv64k does: its cross-validated coverage is 94.4 %
  against 98.45 %. The holdout generalization is reported in evaluations #2 and #3.
- **One machine, one driver, Vulkan only.** HIP could not be tested without a system-wide HIP
  SDK install. GPU clock and temperature were not logged, because no sensor tool was installed;
  drift is controlled by interleaving and canary checks. All sessions used for conclusions
  stayed within ±1.2 %. One Phase 2c session started right after a Windows-update reboot drifted
  +35.5 % and was discarded (JOURNAL, Phase 2c).
- **Single-pass exploratory numbers** from Phase 2 vary between sessions by up to about 15 %
  for the same configuration. Only within-session comparisons and the formal Phase 3 sessions
  support conclusions.
- **Build toolchain:** the reference and final builds use LLVM-MinGW instead of MSVC. The
  reference was validated against the official prebuilt binary (within 1.3 %, identical greedy
  outputs).
- **Target file revision:** the local Gemma target file is an older revision than the file
  currently on Hugging Face (`models/MODELS.md`).
- **llama-bench micro workload (§5.3):** patch 0001 also changes the kernel code that
  single-token decode uses for Q4_K/Q5_K (the loop is restructured; outputs are bit-identical).
  Plain, non-speculative decode speed was therefore measured separately with llama-bench (§4).
